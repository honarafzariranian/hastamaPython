# Residual Risk Register — Hastama

Each risk states the residual exposure **after** the hardening work, the reason
it remains, and the owner. Severities use the same scale as the findings.
"Acceptance" column: whether the risk needs a formal decision by the system
owner before the system is treated as ready.

| RR-28 | **A hand-started `uvicorn` could silently replace the supervised instance.** On 2026-09-28 an unsupervised `uvicorn app.main:app` launched from a VS Code terminal owned `127.0.0.1:5000`; the then-current port-only watchdog reported that state as healthy, the instance ran without the production flags and without the UTF-8 environment, and it died with its terminal (public `502` from 08:27:45 until the port was reclaimed) | Medium | `scripts\watchdog_server.ps1` no longer treats a listening port as health: it identifies the owning process (application signature + production flags + `run_server.bat` supervision or production-log writes), probes `GET /health`, and reclaims the port only from an *identified* Hastama process before re-triggering `\HastamaServer`. Remaining exposure, deliberately not claimed away: an unsupervised or hung instance can serve for up to one watchdog interval (5 minutes) before it is reclaimed — this is detection, not instantaneous prevention; an unrelated application on port 5000 is reported (`PORT_FOREIGN_OWNER`) but never killed; and a process deliberately started with all four production flags whose output is redirected into `logs\hastama-autostart.log` is classified as production (requires administrative intent) | Infra | No |

| RR-29 | **LAN access mode serves plain HTTP on the laboratory address.** The toggled offline fallback (`app/services/lan_access.py`, `master-admin → system settings`) binds the machine's LAN address on port 5000 and relays to `127.0.0.1:5000`, so sessions travel without TLS on that path and the session cookie loses `Secure` there (RR-21). Compensating controls: the listener exists only while an administrator has switched it on and is off by default (the choice is persisted as `system_config.lan_access_enabled` and re-applied at startup); the firewall allow rule is restricted to `RemoteAddress=LocalSubnet` on the `Domain,Private` profiles (nothing reaches the Internet); every forwarding header is stripped and replaced with the real peer address, so audit and rate-limiting records cannot be poisoned and `X-Forwarded-Proto: https` cannot be forced; unparsable requests are answered `400` and never forwarded; one connection carries one sanitised request; the `Host` allow-list gains the LAN address only while the listener runs (never a wildcard); enabling/disabling is audited | Medium | A private address cannot hold a public certificate, so `http://<lan-address>:5000` is unavoidable for the fallback; **no automatic time-out was chosen by the system owner** (2 h / 8 h were declined), which is why the standing exposure is an operator decision rather than an enforced window | Infra | **Yes** |

| RR-30 | **Internet outage mode blocks work for users who still have a working link (false positive) and cuts their sessions.** When the probes declare an outage while the public path actually works (or when an administrator declares it by hand), every page request from outside the laboratory is answered with `503` + the outage page, and the active sessions are terminated (the switch `outage_terminate_sessions` can prevent the cut). The service worker installed in the users' browsers also holds a cached copy of the outage page | Medium | Detecting *the internet* from one host is inherently heuristic and region-specific (a blocked probe target would look like an outage). Compensating controls, all operator-visible: the mode is armed by default but conservative (3 failures 30 s apart, two successes to recover); three independent probe targets where the first success wins; an explicit self-test button (*پایش همین حالا*) showing the last probe detail; a manual override for planned maintenance; and permanent exemptions so the mode can always be switched off — the laboratory listener, direct local requests, an authenticated master administrator and `/health` (the watchdog) are never blocked. Both transitions are audited with the reason, the targets and the number of sessions cut | Infra | **Yes** |

| RR-31 | **Iran-only access refuses legitimate users (false positive) and the shipped address list can go stale.** `app/services/iran_access.py` accepts a public client address only when it falls inside the Iranian allocations of RIPE and APNIC; every other public address is answered with `403` + the VPN warning page and the user cannot work until the VPN is off. The verdict is worse than a heuristic in two directions: a legitimate Iranian user on a range that was allocated *after* the bundled snapshot is refused, and a foreign address inside a range the registry still attributes to Iran is accepted. An unreadable range file disables the filter (fail-open) so it can never become a silent lockout — which means a lost file silently stops enforcing | Medium | The check is offline and self-contained, so it keeps working exactly when the network does not (RR-30) and no visitor address ever reaches a third party. The list ships with the application and is rebuilt only by an explicit administrator action from the two authoritative registries (RIPE + APNIC delegated statistics, ~30 MB, `scripts\refresh_iran_ip_ranges.py` or the card's button); the settings card shows the list version, the range counts and the failure of a refresh. The gate is armed by default but never touches internal addresses (the server itself, the laboratory LAN, CGNAT, link-local — so the LAN fallback of RR-29 is unaffected), the infrastructure paths (`/health`, `/static/`, `/iran-only`, `/offline`, `/sw.js`, `robots.txt`, `sitemap.xml`, `favicon.ico`) or an authenticated master administrator; the verdict is derived from the same single client-address implementation the rest of the application uses, so a forged `X-Forwarded-For` cannot buy an entry. `/iran-only` and `/iran-only/check` let a blocked user (and the warning page itself) see the decision and return automatically once the VPN is off. Blocks are counted and audited (`iran_only_blocked`, throttled to one entry per address per 5 minutes); the switch and the texts are audited as well | Infra | **Yes** |

| RR-32 | **The login loader is a deliberate, configurable *minimum* delay, and the CAPTCHA lifetime is an operator setting.** The default is three seconds of loader before the user lands on the requested page, and a CAPTCHA that stays valid for three minutes. Lowering the lifetime shortens the window in which a code can be replayed; raising it (or lengthening the loader) trades a little friction for legibility on a phone. The loader also covers the page while a request is in flight, so a slow answer no longer looks like a dead button | Low | The loader never delays the request itself — it is a floor on the *display* time, and a failure reveals the real message as soon as that floor passes. The CAPTCHA lifetime is clamped (30–1800 s) in the service and again when the page reads it, so a hand-edited row cannot produce a nonsense value. An expired code is refused server-side either way; the page only *explains* it, and the message now stays on screen (the old refresh helper erased it). Both settings are audited (`update_login_experience`) and validated on save | Product owner | No |

### Mitigations already prepared in the repository

* **RR-25 / RR-26 / RR-27** — implemented and verified on 2026-09-27 (watchdog task installed, dead firewall rule removed, log rotation active). The 271 MB historical log was deleted on 2026-09-28 (`logs\` is back to ~1.4 MB); the rotation in `scripts\run_server.bat` recreates `.log.1` when the live log passes 50 MB.
* **RR-25 (revised 2026-09-28)** — the watchdog no longer treats "port 5000 is listening" as health; see RR-28 for the layered identity/health model, the reclamation path and the incident that made it necessary.
* **RR-30** — implemented 2026-09-28: `app/services/outage.py` (TCP probe in a worker thread, state machine with hysteresis, session cut-off that keeps `MASTER_ADMIN_USERNAMES`, audited transitions), `app/templates/offline.html` (self contained) plus `/offline`, the service worker `/sw.js` and the overlay guard, `_OutageGateMiddleware` in `app/main.py` (503 page / JSON / WebSocket refusal, with the exemption list), and `master-admin/api/outage` (+ `/check`, `/manual`) with the settings card. Behaviour is pinned by `tests/test_outage_page.py` (38 tests: probing, transitions, recovery, audit, settings round trip and validation, the page, the gate and its exemptions, the worker and the endpoints); verified live on 2026-09-28 against a temporary instance on port 5099 (public path → 503 + page with the laboratory address, API → JSON, `/health` `/offline` `/sw.js` and static → 200, laboratory listener → 200, service worker registered and the guide cached, WebSocket refused with 503).
* **RR-32** — implemented 2026-09-28: `app/services/login_experience.py` (validated, clamped loader duration / texts / CAPTCHA lifetime / expiry-notice switch, read by the public page through `/api/system-config`), `app/static/js/script.js` (rewritten: full-screen `login-loader` with a progress bar that fills over the configured duration, rotating status lines, and a request that travels immediately; CAPTCHA lifetime watch polling `/captcha/status`; the expiry message is preserved across the automatic image refresh; the undefined `shake` keyframe replaced by a real `captchaShake`), `app/static/css/login-style.css` (loader + notice styles, dark mode, `prefers-reduced-motion`), `app/templates/login.html` (the busy caption and the green success state removed, the duplicated inline login wrapper deleted, `/api/system-config` feeds `HASTAMA_LOGIN_UX`), `app/services/captcha.py` (configurable lifetime + non-mutating `captcha_expired()`), `app/api/routes/auth.py` (`/login_user` answers `captcha_expired` / `captcha_reason`, `/captcha/status` reports the lifetime), and `master-admin/api/login-experience` with the settings card. Behaviour is pinned by `tests/test_login_experience.py` (35 tests: defaults, clamping, settings round trip and validation, the public config shape, the CAPTCHA lifetime and the four rejection reasons, the absence of the old button sequence, the loader wiring, and the message that survives the refresh).
* **RR-31** — implemented 2026-09-28: `app/services/iran_access.py` (offline verdict from a binary search over merged `(start, end)` ranges, `internal` / `iran` / `foreign` / `unknown` classification, throttled audit, settings, registry refresh, list maintenance), `app/data/iran_ip_ranges.txt` (generated: 1599 IPv4 + 571 IPv6 ranges, 42 KB, RIPE + APNIC delegated statistics), `app/templates/vpn-warning.html` (self contained, RTL, auto-returns once the VPN is off), `/iran-only` + `/iran-only/check`, `_IranOnlyGateMiddleware` in `app/main.py` (403 page / JSON / WebSocket refusal, exemption list, added *inside* the outage gate so a link outage is reported first), `app/core/net.py::client_ip_from_scope` (one shared implementation for the middleware and `Request` paths), and `master-admin/api/iran-access` (+ `/check`, `/refresh`, `/counters/reset`) with the settings card. Behaviour is pinned by `tests/test_iran_access.py` (64 tests: the shipped list and its parser, registry parsing from a fixture, classification of Iranian/foreign/internal/unknown addresses and IPv4-mapped peers, fail-open on an unreadable list, settings round trip and validation, the gate with its exemptions and its master-admin exception, forged forwarding headers, the warning page, audit throttling, counters, the refresh paths and the wiring).
* **RR-29** — implemented 2026-09-28: `app/services/lan_access.py` (byte transparent relay, sanitised request heads, no wildcard host, no auto-off), `master-admin/api/lan-access` (+ `/selftest`), the system-settings card, and `scripts\lan_access_firewall.ps1` with `enable`/`disable`/`status` for the one-time, exactly reversible firewall step. Behaviour is pinned by `tests/test_lan_access.py` (40 tests: address selection, head sanitising, relay end to end, cookie exception, host allow-list, endpoints, persisted flag).
* **RR-28** — the production start path is documented as `\HastamaServer` only: `scripts\start_server.bat` / `stop_server.bat` / `run_dev.bat` (port 5001 for development, never the production port), `disable_autostart.bat` toggles both tasks, and `run_server.bat` carries the warning inline. Verified live on 2026-09-28 (tests A–E in [the supervision report](../HASTAMA_PRODUCTION_SUPERVISION_REPORT.md)).
